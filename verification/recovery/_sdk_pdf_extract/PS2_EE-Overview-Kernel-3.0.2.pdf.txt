Library Overview 
The EE kernel is the operating system running on the EE. The kernel runs in an address space separate 
from applications and provides system calls for priority-based multi-thread scheduling, inter-thread 
communications using semaphores, exception handling, C0P0 control, etc.

1-4    EE Kernel  
Description 
Threads Overview 
Threads serve as the logical unit of programs, as seen from the perspective of parallel processing. The 
processing performed by a single application program is divided into multiple threads, and these threads 
are run simultaneously and in parallel. Since there is only one CPU, however, only one thread will be 
running during any given time slice. Which thread to run is determined by the priority level of the individual 
thread. 
Priority levels are absolute, so if a thread with high priority is running, a thread with lower priority will not be 
executed until the high-priority thread enters a wait state or its state is changed by an interrupt handler. 
This is in contrast to the method used in TSS (Time Sharing System), where multiple tasks (or processes) 
are switched to provide even execution. 
Threads are executed in parallel, but adjustments must be made so that resources such as I/O devices and 
specific work areas in memory can be used exclusively by threads. The EE kernel provides semaphores for 
synchronization between threads. 
A clear distinction is made between threads and interrupt handlers. Threads are executed as part of user 
programs, but interrupt handlers are executed as system programs (even when user-created). 
Thread States and Operations  
Threads managed by the EE kernel have the following seven (or five, depending on how broadly they are 
categorized) states.

• READY: Ready for execution 
The thread meets all conditions for execution but is on stand-by because a thread with higher (or the 
same) priority is running. If there are multiple threads waiting for execution, these threads form a queue 
to wait for CPU availability. This is referred to as a Ready Queue. 
• WAIT: Wait state 
• SUSPEND: Forced wait state 
• WAIT-SUSPEND: Double-wait state 
The thread is stopped since it does not meet conditions for execution. WAIT state occurs when 
execution is stopped due to a system call issued by the thread itself. SUSPEND state occurs when a 
thread has been forced into a waiting state by another thread. WAIT-SUSPEND state occurs when a 
thread is forced into a waiting state by another state when it was already in WAIT state. 
When execution is resumed after a waiting state, execution picks up from where it was interrupted, and 
information representing the execution state of the program (context) such as the program counter and 
the registers are all restored to their original values. 
• DO RMANT: Sleeping state 
This state occurs when the thread has not been activated yet or after it has finished. This state is 
enabled right after a thread is created. 
• NON-EXISTENT: Unregistered state 
An imaginary state that occurs before a thread is created or after it is deleted. A thread goes into 
DORMANT state once it is created, then enters READY state when it is activated and put in the Ready 
Queue. The Ready Queue is ordered by priority levels, with threads having identical priority levels being 
queued in the order they entered READY state. 
Execution is performed for the thread at the head of the Ready Queue, with the thread being placed in 
RUN state. The thread in RUN state enters WAIT state when it waits for a semaphore or an event flag. 
When the wait conditions are met, the thread goes back to READY state.

If an interrupt is generated in this state, control proceeds to the interrupt handler and scheduling is 
performed again when control returns from the interrupt handler. However, execution privilege will not be 
taken from thread B just because an interrupt takes place. Execution of thread B will resume after the 
interrupt handler is finished unless the interrupt handler moves thread A to an executable state or lowers 
the priority of thread B. 
If thread A is put in an executable state by the interrupt handler, thread A will be executable when the 
interrupt handler is finished, and thread B will move from RUN state to READY state. This is referred to as 
"thread B being preempted". In this case, the position of thread B in the Ready Queue remains unchanged, 
so if thread A is removed from the Ready Queue, thread B will be executed. 
Thread priority levels are set to 1 when a user program is started and can be changed to 1-127 using 
ChangeThreadPriority() from the kernel API. The ordering of threads having the same priority level can be 
changed by rotating the Ready Queue using RotateReadyQueue(). For example, if RotateReadyQueue() is 
used for priority level 3, the leading thread will be moved to the end and the ordering will be C, D, B. 
When a thread waiting to be executed is executed, the thread will be placed at the end of the Ready Queue 
for that priority level. 
Semaphores  
When multiple threads are using the same device or buffer areas, the semaphore (signaling) feature allows 
other threads to be notified of the usage status in order to provide synchronization. 
Threads that want to use a device, etc. must acquire the semaphore resource by executing WaitSema(), 
i.e., usage privilege is obtained by setting an in-use flag. Once the thread is done using the resource, 
SignalSema() is executed and the semaphore resource is returned to the system.

The number of semaphore resources can be specified when a semaphore is created. Thus, in addition to 
the exclusion controls described above, semaphores can also be used to indicate the effective data count 
in data buffers shared by multiple threads. When a thread supplies data that is stored in a shared buffer, 
SignalSema() is executed to increase the effective data count. When a thread retrieving the data tries to 
take data from the shared buffer, WaitSema() is executed. If the semaphore resource can be retrieved, the 
data in the shared buffer is processed. If the resource cannot be retrieved, the thread is put in WAIT state 
and waits for data to be provided.

Alarm Feature Overview  
The EE kernel provides 64 alarms that work off of Hsyncs. SetAlarm() can be used to specify an interrupt 
handler for an alarm and the time at which the interrupt handler is called. When the specified time elapses, 
the interrupt handler is called. 
Calling ReleaseAlarm() will release the specified interrupt handler. 
Limitations  
• If interrupts are inhibited for more than 1H, then a call to the alarm interrupt handler will be delayed. 
When that happens, if the alarm interrupt handler's call time has passed the next time it is called, the 
alarm will wrap around. 
• If SetAlarm() and iSetAlarm() are combined to measure time, errors will accumulate because the 
interrupt handler will not be called while interrupts are inhibited. 
Because of the above two limitations, when using alarms, try to use the timer alarm features of the timer 
functions described below, which were added in Release 2.8. 
Timer Feature Overview 
128 BUSCLOCK counters have been provided as part of the EE Kernel timer feature. Each counter has a 
resolution of 868ns, and a worst-case delay of approx. 200us. Counter overhead amounts to an overflow 
interrupt generated once every 6.8V (NTSC). Up to 64 timer alarms are available that use these counters. 
Timer alarms are implemented so that delays will not accumulate. TimerBusClock2Usec() and 
TimerBusUSec2Clock() are provided as conversion functions that enable BUSCLOCKs to be used for 
setting timer alarms.

In the sample programs, etc., the linker script file /usr/local/sce/ee/lib/app.cmd is used. The following are

• Information about the stack area (_stack / _stack_size) 
• Information about the heap area (_heap_size) 
• Entry point (0x00100000) 
• Information about the location and structure of each section

Cache Management and Alignment  
Write-backs from cache to memory are performed in 64-byte units (the size of the cache line). When other 
data is present in the same 64-byte boundary as the data to be written back, this data will be written back 
as well. This can lead to unexpected behavior, so make sure 64-byte alignment is performed on the data. 
File Operations Overview

Interrupt Handler Descriptions 
User-created interrupt processing routines (callback functions) can be registered for various interrupts. 
These callback functions must be programmed with an awareness of the conditions under which they will 
be executed. In many cases, callback functions will be executed as interrupt handlers, but in some cases 
 PlayStation 2 EE Library Overview Release 3.0.2  -  Kernel Libraries 

===== PAGE 25 =====

1-20    EE Kernel  
they may be executed as threads, depending on the library functions and system calls used to register the 
callbacks. 
Interrupt handlers and threads are executed under different system conditions. When programming 
interrupt handlers, the following points must be noted. 
API Differences 
In interrupt handlers, there is no notion of the handler's "own thread". Thus, interrupt handlers in principle 
cannot call system calls that put it in a waiting state or system calls that implicitly specify its own thread. 
Also, due to the implementation, system calls called from threads and system calls called from interrupt 
handlers are sometimes handled differently within the kernel. 
In the EE-Kernel, the number of system calls that can be called from an interrupt handler is restricted, and 
entry names are provided that are distinct from those of the system calls called from threads. As a rule, 
system calls called from interrupt handlers begin with the lower-case letter "i". For example, the 
WakeupThread system call used to wake up a thread will be called as iWakeupThread when called from an 
interrupt handler. 
Stack Differences  
Unlike standard threads, an interrupt handler has a dedicated stack. The stack size is 4 KB. If a larger stack 
needs to be used, the user program should allocate memory. 
Exit Operations  
Call ExitHandler() when an interrupt handler finishes and exits back to normal operations. ExitHandler() 
writes all the instructions saved in the EE's write-back buffer. 
Interrupt Management with DI / EI  
Since the EE kernel implements the disabling and enabling of interrupts with lightweight operations, 
information about whether interrupts are disabled or not is not included in the thread context. Thus, 
problems can occur if threads are switched when interrupts are disabled or when nested DIs/EIs are used. 
Since interrupts are disabled during DI/EI, thread context switching will no longer occur. Although DI/EI can 
also be used to perform exclusive control between threads, it should be used only for short, atomic 
processing. If DI/EI is used over longer intervals, interrupt response time will get worse. In this case, 
semaphores should be used instead for performing exclusive control between threads.

A link error occurs for _ctype_ 
Q.  When I try to link an ERX module, the _ctype_ symbol cannot be resolved and an undefined 
reference to '_ctype' link error occurs. What should I do? 
A.  Define a macro that overrides _cytpe_. 
 
The following link errors may occur when building an ERX module. 
 
undefined reference to '_ctype_' 
undefined reference to '_impure_ptr’ 
undefined reference to '__swbuf’ 
 
These are caused by macros such as isdigit(), which are defined in the libc header file

which is linked to the base ELF. Therefore, to use a macro that is defined in ctype.h in an ERX module, 
define the following macro which will replace a reference to _ctype_ with a call to the __sceErxGetCtype() 
function. 
 
#include <ctype.h> 
extern char *__sceErxGetCtype(void); 
#define _ctype_ __sceErxGetCtype()

Module loader asynchronous function won’t end 
Q.  Asynchronous module loader functions don't seem to work properly. Why does sceErxSync(1) 
continue to return 1 no matter how long I wait? 
A.  Check to see if any threads are running at a higher priority. 
 
Asynchronous module loader processing is performed by the module loader thread. Since this thread is 
executed at the priority that was specified with sceErxInit(), if a thread having a higher priority has taken 
away the execution right, asynchronous module loader processing will not end. Leave some room for the 
module loader thread to run by placing threads having a higher priority than the module loader thread in an 
appropriate WAIT state. 
This problem tends to occur when sceGsSyncV() is used to wait for VBLANK. This is because 
sceGsSyncV() waits for the start of the VBLANK period by internally polling without entering a WAIT state. If 
sceGsSyncV() is used, the execution right will not be passed to other threads. 
To make other threads run while waiting for VBLANK, use a semaphore instead of calling sceGsSyncV(). To 
make this work, sceGsSyncVCallback() should be used to register a callback function in advance, then the 
thread waiting for VBLANK calls WaitSema() and enters a WAIT state. The callback function should then 
call iSignalSema() to cancel the WAIT state. An example of this technique is shown below.

#include <eeregs.h> 
#include <libgraph.h>

{ 
    (void)cause;                        // Suppress warnings for unused

Q.  Why did a TLB error occur after I migrated an existing program to ERX? 
  The program seems to stop on load and store instructions which use the $gp register for 
addressing. 
A.  You must add code to adjust the value of the $gp register in your program.

normally does not change until the program ends. By comparison, in the ERX environment, each ERX 
module has a _gp symbol, and code within each module expects that the value of the $gp register 
matches the address of that module's _gp symbol.

crosses a module boundary. As a result, if the $gp register is used within a module, the address of that 
module's _gp symbol must be set in the $gp register when the function is called from another module. 
Furthermore, when returning from the function, the $gp register value must be restored to its original value.

Loading a module asynchronously 
Q.  How do I perform other processing while I'm loading a module? 
A.  You can either use the asynchronous version of the module loader functions or you can use 
another thread to perform the additional processing. 
 
Besides using a function to load a module asynchronously, you can start up another thread to perform the 
additional processing, then use the synchronous version of the module loader function. 
When another thread is used, its priority must be set appropriately. Note that just invoking 
sceErxLoadModuleFile() causes the command to enter a WAIT state, while the load operation itself is 
performed by the module loader thread. This means that priorities must be adjusted between the thread 
that performs the additional processing and the module loader thread. 
The priority of the module loader thread can be specified when liberx is initialized. Since the module loader 
thread is responsible for calling the entry function, it should be assigned a high priority to the extent 
possible. However, care should be taken so that the execution right is passed appropriately to each thread 
so that asynchronous processing can be performed as described above. 
Loading without using a temporary buffer 
Q.  How can I load a module without using a temporary buffer?

buffer can be reduced.

SCE_ERX_ACCESS_SEEKMANY in the mode argument of sceErxLoadModuleFile(), you can reduce the 
amount of space used for the temporary buffer. However, since this will make the loader read the ERX file 
only a little at a time into the small buffer, it will take longer to load the module. Also, this method cannot be 
used to read a compressed or encrypted ERX file.

Self-unloading operation 
Q.  When the sceErxSelfStopUnload() function is called, an ERX module is stopped and unloaded. 
However, shouldn't processing try to transition to the unloaded memory when it returns from 
this function? 
A.  When unloading succeeds, processing does not return because the thread that called the 
function within liberx is deleted. When unloading fails, processing does return from the function, 
but in this case no problem occurs because the thread is not deleted. 
 
When the sceErxSelfStopUnload() function succeeds and the module is unloaded, processing does not 
return to the caller. The called thread is automatically deleted internally within liberx. 
When processing for stopping the module fails, the sceErxSelfStopUnload() function returns with an error. 
However, in this case, since the module has not been unloaded, subsequent processing can safely 
continue.

Library version 
Q.  Why would the library version cause dynamic linking to fail? 
A.  A dynamic link will fail when there is a mismatch between the high-order 8 bits of the library 
versions, or when the low-order 8 bits of the version is larger on the import side. 
 
liberx determines whether or not libraries can be linked by comparing the library name and library version 
number in the entry table on the export side (side making the library publicly available) with the library name 
and library version number in the stub on the import side (referencing side). 
The library version number is a 16-bit value and the high-order 8 bits together with the library name identify 
the library. When the library identifiers do not match between export side and import side, the libraries are 
considered to be incompatible and are not linked. 
The low-order 8 bits of the library version number are used for determining upward compatibility. In other 
words, when the low-order 8 bits of the version number specified by the import side are greater than the 
low-order 8 bits of the version number held by the export side, the export side is considered not to satisfy 
the specifications expected by the import side and the libraries are not linked.

Interrupts used by the DECI2 ELOADP driver 
Q.  Does the DECI2 ELOADP driver use interrupts? 
A.  Yes, the DECI2 ELOADP driver uses the INTC_VBLANK_E interrupt handler for performing 
extremely lightweight processing. 
 
The DECI2 ELOADP driver must perform a regular polling operation on the target (EE), so it uses the 
INTC_VBLANK_E interrupt handler of the EE kernel. Since it doesn't do anything except to call the 
ExitHandler() as long as there aren't any requests from the debugger, it has practically no effect on 
performance. 
Contention between the DECI2 ELOADP driver and the interrupt 
Q. I want to use INTC_VBLANK_E in my own program. Will this interfere with the DECI2 ELOADP 
driver? 
A.  If suitable procedures are used for registering and removing the interrupt handler, more than one 
interrupt handler can be allocated to INTC_VBLANK_E. 
 
The EE kernel can register more than one interrupt handler for a single interrupt cause. Since these 
handlers are called continuously when interrupts occur, the DECI2 ELOADP driver and another program 
can share the use of the INTC_VBLANK_E interrupt. As an example, the USB keyboard library libusbkb 
created by SCE uses the INTC_VBLANK_E interrupt along with the DECI2 ELOADP driver. 
To safely share the INTC_VBLANK_E interrupt, suitable procedures must be used for registering and 
removing the interrupt handler. Specifically, to register an interrupt handler, perform the following steps: DI() 
 AddIntcHandler()  EnableIntc()  EI(). Then, to remove the interrupt handler, perform the following steps: 
DI()  RemoveIntcHandler()  DisableIntc()  EI(). However, DisableIntc() can only be called when the handler 
that was removed is the last handler for that cause. If the DisableIntc() function is called while another 
handler still remains, processing will be stopped. See the following sample code.

as it does on a PS2 console or on the DebuggingStation, which means that the dselist and dsestart utilities 
and dsedb's mlist command can no longer be used.

-G0 option when building 
Q.  When I build an ERX module, should I add the -G0 option to CFLAGS? 
A.  Specifying the -G0 option means that processing related to the $gp register can be omitted. 
However, this will occasionally cause redundant code to be generated, leading to a decrease in 
performance. 
 
When an ERX module is compiled with the -G0 option specified in ee-gcc, no code will be generated that 
uses the $gp register. Since the _gp symbol is defined for each ERX module, when the $gp register is 
used, its value must be reset appropriately for each module. A simple and reliable method of eliminating 
this task is to specify the -G0 option so that the $gp register will not be used. However, if the -G0 option is 
specified, the code that is generated for accessing a global variable inside the module may become a little 
redundant. 
If functions which are called from other modules properly set and restore the $gp register, then there is no 
need to specify the -G0 option. 
It should be noted that SCE uses the -G0 option when building its runtime libraries and the toolchain. 
Location of ERX and ILB files 
Q.  I want to use ERX versions of libraries provided by SCE. Where are these files located? 
A.  You can find the files in the sce/ee/modules/ and sce/ee/ilb/ directories. 
 
ERX files are installed in the /usr/local/sce/ee/modules/ directory. 
ILB files are installed in the /usr/local/sce/ee/ilb/ directory. 
Loading ERX module symbols in dsedb 
Q.  How can I load symbolic information for ERX modules into dsedb? 
A.  Use the sload command. 
 
To load symbolic information for an ERX module, use dsedb's sload command. If the program is running, 
dsedb uses the ELOADP and ESDBGP protocols to find the address where the module is loaded and uses 
that address to load relocated symbolic information. 
Using ee-gdb 
Q.  I normally use ee-gdb. How can I debug ERX modules using ee-gdb? 
A.  ERX modules are not supported by ee-gdb. 
 
ee-gdb does not have any functions to support ERX module debugging. In particular, it is not possible to 
read symbolic information for multiple modules when more than one module is loaded. 
However, it is not the case that ee-gdb can never be used. For example, the dselist and dsestart utilities 
can be executed in another window while ee-gdb is running. This allows these utilities to be used while 
debugging.

TBL file entries 
Q.  What is the 8 in Entry/8, which appears in the description of the library entry definition file (TBL 
file)? 
A.  It defines the public level of a library function. 
 
When a library function is described in an Entry line of the TBL file, a "public level" can be declared. The 
public level is referenced when the eelibgen utility generates an ILB file based on the TBL file. At that time, 
only functions having a public level up to the public level specified by the -l option appear in the ILB file. For 
example, assume that the entries had been described as follows in the TBL file. 
 
Entry     PublicFunction 
Entry/1    HiddenFunction 
 
The public level is 0 when the -l option is not specified. In this example, only PublicFunction is included in 
the ILB file and can be called across modules. If a value greater than or equal to 1 is specified as the public 
level, HiddenFunction can also be called across modules. The function entry itself is present in the library 
regardless of the public level. 
Situations in which an ILB file is required 
Q.  When is an ILB file required? 
A.  An ILB file is required when dyna mic linking across modules is performed. 
 
An ILB file is required when dynamic linking across modules is performed for a function that has been 
exported from some other ERX module. Specifically, it is required in the following cases. 
• When an ERX module’s function  is called from the base ELF 
• When an ERX module’s function is called from some other ERX module 
• When a library function that was statically linke d to the base ELF is called from an ERX module 
In other words, a library developer should provide an ILB file when he wants to have other modules call his 
library's functions. 
People developing libraries for use within the company and T&M licensees should consider creating ILB 
files and supporting ERX.

 ERX Programming (Beta Version)    3-3 
Overview 
Modules 
The EE kernel assumes that only one program will be running in EE memory. On the other hand, the IOP 
kernel does allow more than one program to be loaded into IOP memory. liberx is a library in which the IOP 
kernel's system memory management functions, module management functions, and library management 
functions have been ported to the EE kernel, making them available on the EE in a module environment 
equivalent to that of the IOP kernel. 
An EE object file normally has an ".erx" extension and is known as an ERX file. A program that is relocated 
when it is loaded into memory from an ERX file is called a program module, or simply a module. 
Each module has one entry routine (usually, a start function). The entry routine is called when the module is 
loaded and its return value determines whether or not the module is made resident in memory. In an ERX 
file, the entry routine may also be omitted. In this case, the module is implicitly made resident. 
Lifetime of Modules (Resident / Non-resident) 
During the time that they are loaded in memory, modules can be classified into different types. 
One type is a module whose entry routine is executed only once; after its purpose has been fulfilled, it is 
deleted from memory. This type of module is referred to as a "non-resident module." 
Another type of module, the resident module, remains in memory even after its entry routine has completed 
execution. This type does its processing when there is a request from another module or an interrupt. 
Modules containing entries that are called as subroutines from other modules are referred to as "resident 
libraries." 
Some resident modules can be deleted from memory when they are no longer needed; these are referred 
to as "unloadable resident modules." 
Program Loader 
The program loader handles the loading and relocating of program modules from CD/DVD-ROMs, etc, and 
manages modules in memory. 
The program loader consists of a lower-layer module manager and a higher-layer file loader. 
The module manager does the following: 
• Examines erx-formatted object data provided from the file loader, and relocates objects. 
• Performs linking between loaded modules. 
• Registers and deletes entry tables of resident-library functions. 
The file loader does the following: 
• Loads and starts object files from disk. 
• Registers and deletes modules.

Module Loading and Starting 
As directed by the sceErxLoadStartModule() API, etc, the program loader loads the ERX object file and 
calls the module's entry routine. The value returned by the entry routine determines whether or not that 
module will remain resident in memory or be deleted. 
Load and Start-up Procedure 
Loading a module and calling its entry routine involves the following steps: 
1. Search for object data with an ERX object file format; if necessary, allocate memory, and after 
reading in the object, relocate it. 
2. Zero-out the module's BSS segment. 
3. Assign a module ID to the module. 
4. Check the .erx.stub section of the module and resolve links of library functions imported by the 
module. 
5. Register any libraries that will be implicitly exported by the module. 
6. Call the module's entry routine. 
7. Determine whether the module is resident or not based on the value returned by the entry routine 
and perform processing accordingly. 
8. When the module is made non-resident, cancel the registration of any libraries that were exported. 
9. Cancel the importing of any functions that were imported by the module.

Importing Module Functions 
When a module starts up, functions are imported so that library functions provided by another module can 
be used. However, if a library is needed by the module but it has not yet been registered, 
sceErxStartModule() will return the error SCE_ELIBACC, and the module will not be allowed to start up. 
The IOP kernel imports module functions when a module is loaded. However, the liberx library behaves 
differently in that module functions are imported when the module starts up. This means the order in which 
the modules are loaded will not be affected by the dependency relationships between the modules. In other

Entry Routine 
A module's entry routine can have the following prototypes. IRX requires that the entry routine be 
implemented, however, with ERX the entry routine may be omitted. 
int start(int reason, int argc, const char *const argv[]); 
The program loader activates a thread allocated for executing the entry routine; that thread calls the entry 
routine through the following procedure: 
1. Push the argv[] array and argument strings onto the stack. 
2. Set the module's global pointer value to the GP register ($28). 
3. Call the entry routine with SCE_ERX_REASON_START as the reason code. 
4. Based on the lower 2 bits of the value returned by the entry routine, determine whether the 
module is resident or non-resident. 
5. Thread complete. 
Module programmers must arrange for entry routines to be run in the following environment: 
• Stack size for execution threads: within 2 KB. 
• Made to run independent of the executable thread priority (the entry routine is actually called with 
the thread priority specified by sceErxInit()). 
• reason should be the reason code called by the entry routine (SCE_ERX_REASON_START) 
• argc: same as general C-language main function arguments (one or more). 
• argv: same as general C-language main function arguments 
Because only one thread is allocated for executing entry routines, as a general rule, it is not possible to 
execute entry routines from different modules in parallel. So it is not necessary to take into account conflicts 
with entry routines from other modules with the entry routine of an ordinary module. In rare circumstances, 
one entry routine may call LoadStartModule() or a related API to start up another module. When this 
happens, the execution of entry routines is nested, and as a result, the usable stack size is reduced. 
Although the IOP kernel guarantees that the module loader thread runs at a high priority 
(MODULE_INIT_PRIORITY=8), liberx leaves the priority of the thread called by the module's entry routine up 
to the discretion of the application programmer. This is because the thread runs with the priority specified 
by sceErxInit(). ERX module programmers must not depend on the priority of the thread called by the entry 
routine.

freely used by the programmer.

Stopping and Unloading Modules 
Resident modules whose entry routines return SCE_ERX_REMOVABLE_RESIDENT_END are recognized 
by the program loader as unloadable resident modules, and can be deleted when they are no longer 
resident using the sceErxStopModule() and sceErxUnloadModule() APIs. 
Stop and Unload Procedures 
The program loader allocates the memory area that will store the module itself when the resident module is 
loaded. When the module is unloaded, it frees that memory area. If there are any other resources that were 
allocated in the course of the module's execution (memory, threads, event flags, semaphores, etc), 
because these fall outside the program loader's control, they must be freed by the resident module itself.  
As such, unloading a module is a two-step process. First, a stopping process is performed by the module 
that frees resources. Then the module manager deletes the resident module from memory. 
A resident module is stopped by calling the sceErxStopModule() API. When executing sceErxStopModule(), 
the program loader activates a thread allocated for executing the entry routine, then calls the entry routine 
with the following procedure: 
1. Push the argv[] array and argument strings on the stack. argv[0] must always be set to the string 
"other". To indicate a stop processing call, set the reason argument to 
SCE_ERX_REASON_STOP. 
2. Set the module's global pointer value to the GP register ($28). 
3. Issue a subroutine call to the entry routine. 
4. (Execute the module entry routine. The reason argument will be SCE_ERX_REASON_STOP, and 
processing such as freeing resources will be performed.) 
5. If the lower 2 bits of the value returned by the entry routine are SCE_ERX_NO_RESIDENT_END, 
then the stop process succeeded, and the module is considered to be in the stopped state. If the 
return value is SCE_ERX_REMOVABLE_RESIDENT_END, the stop process failed, and the module 
is considered to still be in an operating state. 
6. When the module is resident, if any libraries exist that had been implicitly exported, cancel their 
registration. 
7. Cancel the importing of any library functions used by the module. 
8. Thread complete. 
Resident modules are deleted using the sceErxUnloadModule() API. This API makes sure that the target 
module is in a stopped state, then deletes the module's registration. Memory that had been automatically 
allocated for the target module at load time is now freed.

Resident Library Organization

automated for liberx.

Reference: Linking Between Modules 
When loading a module, the ERX program loader checks to see whether that module calls any 
already-loaded modules (resident libraries), and links to other modules if necessary. The linking function 
acts on the entry-table structure in the resident library being called, and on the call-table structure in the 
module making the call. 
Entry-table Structure 
The set of functions the resident library provides to other modules is recorded in an entry-table structure as 
described below, and using the program loader's sceErxRegisterLibraryEntries() API, are registered with the 
system when the modules are activated according to the modules themselves.

These files, which have ".ilb" file extensions, are text files with a fixed column format as shown below: 
 
#EE-ILB# insert any text here  
L library name

column of the line, and the entry name beginning from the line's seventh column until the end of line.

Checking Compatibility When Linking 
As mentioned above, the entry-table structure and call-table structure both have fields for library names 
and versions.  
The library name is 8 bytes; if the name itself is fewer than 8 bytes, it should be padded with null 
characters. The upper 8 bits of the version field represent the library's major version number; the lower 8 
bits the minor. 
In general, the version field can be set to any value in the program, with the following stipulations: 
Major version numbers must be set so that if function table ordering and function specifications are 
compatible, the numbers must be the same. 
Minor version numbers are incremented to reflect bug-fixes and additional functionality for backwards 
compatibility. 
Major and minor version numbers both must be 1 or greater. Zero should not be used. 
When a module is loaded in EE memory and the call table structure which it contains is linked, a search is 
performed to find registered entry table structures that have a library name field that matches the major 
version and which have a minor version number that is greater than or equal to the minor version specified 
in the call table. If any such structures are found, they are linked. 
In the current IOP kernel, entry table structures can be linked even when the minor version of the entry 
table structure is less than the minor version of the call table structure. However, in the liberx library, a 
stricter comparison is performed. 
When the entry-table structure is registered with the system, even if the library name and major version 
match those of the registered library, if a higher minor-version exists, then registration will fail.

Issues related to relocation table entries, other than those which are described below, are the same as for

Objectives of the ERX System 
The ERX system enables dynamic link libraries to be used on the EE through the use of relocatable object 
modules. It consists of liberx, which is the platform for executing ERX modules and various utilities for ERX 
development, as well as DECI2 and dsnet which have been extended to support ERX. 
The ERX system implements on the EE an environment similar to the program execution environment on 
the IOP. It also offers additional benefits like improved memory utilization and a convenient way to provide 
libraries.  
Runtime libraries provided by SCE are now available in the ERX format in addition to the conventional 
format. 
Improved Memory Efficiency 
By using ERX modules, a program can be divided into small units. ERX modules can be placed in memory 
with more freedom than overlays, making it easier to only place programs in memory that need to be 
executed. 
In addition, libraries provided as ERX modules can easily be used together with libraries that are designed 
to be statically linked to ELF files. If a library is provided in both formats, the programmer can decide which 
format to use. 
Improved Library Independence 
By using ERX modules, the application program and the libraries can be separated into independent files. 
Since this allows libraries to be updated without touching the actual application, more freedom can be 
achieved during the development process. If debugging code has been implemented in the library it 
becomes simpler just to switch to a release version of the library when debugging is completed. Also, if a 
problem occurs, the library provider can easily examine the problem without touching the actual 
application. 
Program Encryption 
ERX modules can be executed while they are encrypted. Distributing a program as an encrypted ERX 
module can prevent others from cheating or analyzing the program. An encrypted ERX module can also be 
saved on a Memory Card (PS2) or the PlayStation BB Unit. In the future, there are plans to distribute 
patches over the network using a mechanism based on encrypted ERX modules.

ERX System Design 
This chapter, which is mainly for reference when developing applications, explains the design of the ERX 
system and describes how ERX modules are executed. For more detailed information, please refer to the 
liberx library overview and reference documents, and the "ERX Programming" document. 
Role of liberx 
liberx is a library that creates an environment in which ERX modules can be executed within the 
environment provided by the EE kernel. 
An application that uses ERX modules first starts a conventional monolithic ELF program file (the base ELF) 
in the ELF execution environment provided by the EE kernel. Then, an environment in which ERX modules 
can be executed is created within the ELF execution environment by initializing liberx.a, which is statically 
linked to the base ELF. Dynamic loading and unloading of ERX modules and dynamic linking with the ELF 
file are implemented in this ERX execution environment.

Memory Management 
The ERX system enables memory to be used flexibly. 
When an application (the base ELF) initializes liberx, an arbitrary memory area is allocated in advance and 
designated as memory to be managed by liberx. An ERX module is normally loaded and executed in this 
liberx-managed memory. Normally, liberx will automatically determine the load address, however, the 
address can also be specified when the module is loaded. It is also possible to load an ERX module in 
separately allocated memory such as within the libc heap.

Dynamic Linking of Functions 
An ERX module can provide its internal functions to the base ELF or to another ERX module. In other 
words, you can make the internal functions of an ERX module available to be called from another program. 
This kind of ERX module is called a resident library. 
Since the addresses of the internal functions of a resident library are determined when the resident library is 
loaded into memory, a dynamic linking mechanism is needed so that these functions can be called from 
another program. Dynamic linking is implemented in the ERX system by having the resident library and the 
calling program each keep a list of functions, then rewriting the calling program's list when liberx is 
executed. 
The list of functions that a resident library provides to another program is called the entry table structure. 
Since the address of each function is determined when the resident library is loaded into memory, liberx 
automatically reads the entry table structure and enters its contents along with the addresses of each 
function in an internal table. 
On the other hand, the list that the calling program has, indicating which functions from which libraries are 
called, is called a stub or call table structure. 
When an ERX module is started, the address of each function is written to the stub kept by the module, 
based on the contents of the registered entry table structure. As each module provided by that library is 
started, the addresses of its respective functions are written to the stub kept by the base ELF.

===== PAGE 83 =====

Resident library functions whose addresses are determined at execution time can be called from another 
program via the stub that is created in this manner. The stub actually consists of J instructions from the 
MIPS instruction set. In other words, the overhead to perform dynamic linking amounts to two instructions, 
the J instruction and the instruction in its delay slot. 
The mechanism for calling a library that is statically linked to the base ELF from an ERX module is also 
implemented in the same way, using an entry table structure and stub. Since the only difference between 
static and dynamic linking is that with dynamic linking the entry table structure must be explicitly registered, 
changing a library from statically linked to dynamically linked or vice versa, can be easily done just by 
making simple changes to the base ELF. 
Resident and Non-Resident Modules 
ERX modules can be divided into two main types according to how long they reside in memory. 
The first type, which stays in memory after it is loaded, is a module that performs processing whenever it is 
called from another program or because of an interrupt. This kind of module is called a resident module 
(the resident library described earlier provides subroutines to another program within a resident module). 
The second type of module is one that is loaded and executed once and then removed from memory once 
its purpose is completed. This kind of module is called a non-resident module. 
Whether or not a module is actually made resident is determined by the value returned by the entry function 
that is called when the module is loaded. For a resident module, the entry function that is called when the 
module is loaded performs initialization processing and returns a value that indicates that the module is 
made resident (SCE_ERX_RESIDENT_END or SCE_ERX_REMOVABLE_RESIDENT_END). On the other 
hand, for a non-resident module, the entry function performs processing required for the module and 
returns a value that indicates that the module is not to be made resident (SCE_ERX_NO_RESIDENT_END). 
liberx removes the module from memory according to this value. Using this mechanism, a resident module 
can be prevented from staying resident if a problem occurs when the module is initialized. 
Unloading a Resident Module 
You can create a resident module that can be removed (unloaded) from memory when it is no longer 
needed. An unloadable resident module can be used as a means of replacing a section of a program, like a 
conventional overlay. 
A resident module is unloaded in a two-stage process. First, stop processing is performed to free 
resources that are being used by that module. Then, after confirming that the module has been stopped, it 
is removed from memory. This two-stage process is generally implemented by another program such as 
the base ELF. However, the resident module can also do this processing itself by creating a separate 
thread. This kind of resident module is called a self-unloadable resident module. 
By comparison, the method for using overlays is not as well structured. Operations such as managing 
memory where overlay programs are located and appropriately freeing resources that are used by those 
programs are the responsibility of the application programmer. When overlays are replaced with unloadable 
resident modules, the burden on the programmer can be reduced. (It is not always true that this burden 
can be eliminated immediately. In particular, when an existing library is converted to an unloadable resident 
module, the benefits offered by ERX modules may not be fully realized because existing specifications need 
to continue to be supported. Even the runtime libraries provided by SCE have many remaining un-ERX 
module-like constraints.) 
Entry Functions 
As a general rule, each ERX module has one entry function. Although there are no special rules or 
restrictions as to the name of the entry function, usually "start" is used.

As mentioned earlier, the entry function is called from liberx when the ERX module is started. For a non-
resident module, the entry function performs the actual processing for the module. For a resident module, 
the entry function has the job of performing initialization processing to determine whether or not the module 
should remain resident in memory. It is also responsible for stopping the module. 
Whether if performs initialization or stop processing is specified by the first argument named "reason" when 
the entry function is called. In other words, the entry function of a resident module first determines the value 
of the "reason" argument and then performs initialization processing if the value is 
SCE_ERX_REASON_START or performs stop processing if the value is SCE_ERX_REASON_STOP. 
The entry function can be omitted under special conditions. A resident module which does not make use of 
any resources, and therefore does not need any initialization or stop processing, does not need to have an 
entry function. 
The entry function can also be omitted when APIs for performing initialization and stop processing have 
been implemented separately. However, in this case, the application programmer is responsible for calling 
the initialization process after the module is started and calling the stop process before the module is 
unloaded. Consequently, it is possible that a bug could cause the module to be removed from memory 
without it being stopped first. A module will be safer and easier to use if initialization and stop processing 
are implemented by the entry function. 
Reference: Differences with the IOP Kernel 
Although the structure and behavior of liberx have been modeled after the IOP kernel, several differences 
do exist. 
Hybrid structure of base ELF and ERX modules 
While an IRX module is executed on top of the IOP kernel, an ERX module is executed on top of the base 
ELF. To the EE kernel, this has the same structure as a monolithic ELF program since liberx creates the 
ERX module execution environment at the library level. 
This hybrid structure allows an application programmer to decide whether a library required by the program 
should be statically linked to the base ELF or dynamically linked as an ERX module, depending on the 
particular situation. 
Coexistence with libc heap (malloc and free) 
liberx manages only the memory that was specified during initialization. It does not use the libc heap at all, 
however, an ERX module can use the libc heap by calling a libc function such as malloc() via the stub 
library. 
Elimination of Dedicated Memory Area for Loading Modules 
The IOP kernel has a function that allocates memory specifically for loading modules and loads modules at 
specified addresses within that area. liberx does not have this function. 
Automatic Registration of a Library Exported From an ERX Module 
The IOP kernel requires an IRX module that exports a library to register the library entry table in the IOP 
kernel by calling the RegisterLibraryEntries() function. 
In contrast, if an ERX module has a library entry table, liberx automatically registers the library when that 
module is started. Furthermore, the library registration is automatically canceled when the module is 
stopped. However, the sceErxRegisterLibraryEntries() function must be explicitly called for a library that is 
statically linked to the base ELF.

Resolving Library Links Between ERX Modules at Module Start Time 
In order for the IOP kernel to resolve library links that span more than one IRX module when the modules 
are loaded, the order in which the modules are loaded is restricted by dependencies between the modules. 
In contrast, liberx resolves library links that span more than one ERX module at module start time. 
Therefore, modules can be loaded in any order, but the order in which modules can be started is restricted 
by dependencies between the modules. 
Self-Stopping and Self-Unloading of Modules 
The IOP kernel provides separate APIs for self-stopping and self-unloading modules. However, liberx 
provides only sceErxSelfStopUnloadModule(), which performs self-stopping and self-unloading as an 
atomic operation. 
If these functions were implemented as separate APIs, it would not be possible to call the self-unloading 
function because liberx deletes library links when a module is stopped. 
Ability to Omit the Entry Function 
An entry function must be defined in an IRX module. However, the entry function can be omitted in an ERX 
module. 
If an ERX module does not specifically use any resources and therefore does not need to initialize or free 
those resources, it is not necessary to create an entry function. Likewise, an entry function does not need 
to be created when the application programmer takes responsibility for initializing and freeing the resources 
used by the ERX module, just like with a conventional overlay. 
Differences in the Prototype Declaration for the Entry Function 
The prototype of the entry function for an IRX module is as follows. When the module is to be stopped, 
argc is made a negative value to indicate the reason for the call. 
 int start(int argc, char *argv[]); 
By comparison, the prototype of the entry function for an ERX module is as follows. 
 int start(int reason, int argc, const char *const argv[]); 
Since the reason argument was added to indicate the reason why the module is being called, argc should 
not be made a negative value to stop the module. 
Invoking a Call to Stop the Module for a Non-Resident End 
With the IOP kernel, when the entry function terminates with a non-resident end, the entry function is not 
called again to stop the module. 
With liberx, even when the entry function returns SCE_ERX_NO_RESIDENT_END to represent a non-
resident end, the entry function is called again with the reason argument set to SCE_ERX_REASON_STOP 
to indicate that the module should be stopped. 
 Asynchronous Operation of the Module Loader 
liberx provides both synchronous and asynchronous versions of functions that load modules. The 
synchronous versions block until processing has completed, while the asynchronous versions return 
immediately and only register the load process. 
With the asynchronous versions, the module loader thread performs the actual processing for loading the 
module, and the original thread that called the function can check to see if the load has completed by 
polling periodically. However, note that load processing will not advance unless the module loader thread 
obtains the execution right. A thread having a higher priority than the module loader thread must enter an 
appropriate WAIT state so that the execution right can be given to the module loader thread.

Precautions When Programming 
Use of global variables 
Since links between liberx modules can only support function calls that cross module boundaries, global 
variables that span modules cannot be defined or referenced. To share a variable between modules, define 
a function so that it returns the address of that variable. 
Among the libraries provided by SCE, libhig uses a global variable named sceHiErrState. However, runtime 
library 2.8 introduced a function named sceHiGetErrStatePtr(). Therefore, programs that use libhig must be 
modified. 
About $gp 
With a monolithic ELF program, the $gp register is initialized with the address of the _gp symbol, and the 
same value is normally used for the entire program. In contrast, each ERX module has a _gp symbol, and 
code within each module runs under the assumption that each module has a different $gp register value. 
However, liberx does not have a function that adjusts the value of the $gp register when one module calls a 
function in another module. As a result, if the $gp register is used in one module, it must be set 
appropriately before calling a function from another module, and it must be returned to its original value 
when returning from the function. An example is shown below. 
 
#include <eekernel.h> 
 
int ExportingFunction(int arg) 
{ 
    int res; 
 void *oldgp = SetModuleGp(); // Set $gp register to _gp symbol 
address 
 res = InternalFunction(arg); // Call internal function using $gp 
register 
 SetGp(oldgp);   // Restore original $gp register value 
 return (res); 
} 
 
Another simple and reliable method is to specify the -G0 option when compiling the module. If the -G0 
option is specified, the $gp register will not be used within that module. Therefore, the processing for 
setting and restoring the $gp register value as shown above is unnecessary. However, code efficiency may 
decrease somewhat when global variables are referenced. 
Note that the -G0 option was specified when SCEI built its runtime libraries and the toolchain. In addition, 
beginning with runtime library 2.8, in order to use the $gp register in a callback function the EE libraries 
were unified according to the following rule:  the value of the $gp register is saved when the address of a 
callback function is registered, and that value is set in the $gp register when the callback function is called. 
(Note that this works differently on the IOP.)

About the base ELF 
Unlike the IOP kernel, the ERX environment of liberx as it is implemented on the EE has a hybrid structure 
consisting of a base ELF together with ERX modules. However, the usual procedure for starting a 
monolithic ELF has not changed since even a program which incorporates ERX modules will start the base 
ELF first. The ELF program is initially started by calling the EE kernel's LoadExecPS2() function, or it can be 
started from a debugger such as dsedb. 
About multithreading 
liberx runs the module loader thread and the ELOADP driver thread. The priorities of these threads can be 
specified when liberx.a is initialized using the sceErxInit() function. 
Therefore, to properly perform operations such as loading modules, you must carefully consider the 
behavior of other threads that will be running at the same time, so that the execution right can be passed to 
the module loader thread at the appropriate time. 
For example, if a thread that has a higher priority than the module loader thread calls sceGsSyncV() in order 
to wait for VBLANK, the execution right will not be passed to the module loader thread because 
sceGsSyncV() will be performing a polling operation. To run the module loader thread while waiting for 
VBLANK, the thread waiting for VBLANK must relinquish its execution right. A technique for accomplishing

Migrating to ERX 
To migrate your code to the ERX system, use any of the techniques listed below. 
• Without making major changes to user programs, replace the static versions of libraries with their 
corresponding ERX versions. 
• Convert programs that are structured as overlays into the ERX format. 
• Change statically linked libraries so they can be used from ERX modules. 
• Co nvert statically linked libraries to ERX-formatted libraries. 
The main points of each of these migration steps are explained below. 
Replacing Libraries 
To change a program that uses the statically linked version of a library (.a format) to one that will use the 
ERX version of the library, you must add initialization processing to link liberx.a and set up the ERX 
environment. 
Initialization processing consists of registering each library's entry table in liberx so that ERX modules can 
use the functions of the statically linked library, in addition to calling sceErxInit() using the prescribed 
procedure. Then, when building the base ELF, a procedure is also required for linking the stub instead of 
the actual library. See the following sample programs. 
• sce/ ee/sample/inet/libnet/http_get/ 
• sce/ ee/sample/inet/libinsck/http_get/ 
• sce/ ee/sample/timer/fps/ 
• sce/ ee/sample/libeenet/http_get/ 
• sce/ ee/sample/netglue/* 
 
In terms of changes to internal processing within the program, check to make sure that inappropriate 
polling is not being done which could prevent the module loader thread from running properly. In particular, 
problems often occur because sceGsSyncV() is used to wait for a VBLANK. Replace this with a method 
appropriate for multithreading such as waiting for VBLANK using a semaphore. 
Converting Overlays to the ERX Format 
To convert a program that uses an overlay structure into the ERX format, you must export functions in the 
base ELF that are called from the overlay sections so that they can be called from ERX modules. The 
migration steps are similar to those needed to provide ERX support for statically linked libraries. 
The following steps must be performed for the overlay sections.

Adding ERX Support to Static Libraries 
To enable a library that is statically linked (.a file) to be called from an ERX module, perform the following 
steps. 
First, as preparation, review the library specification beginning with the APIs so that you can determine how 
the library can be most easily adapted to the ERX environment. Specifically, perform the following steps. 
• Make sure global variables cannot be directly accessed publicly.  
liberx only supports links for functions. Since variable-level links cannot be used, when a publicly 
available variable is used globally, be sure to add a function to return the address of that variable. 
• Check to see whether or not library functions that are provided by the toolchain such as libc.a, 
libm.a, or libgcc.a must be used in the library. In an ERX environment, since a group of functions 
is handled as a logical library, there is a risk that when library functions are called inadvertently, the 
number of dependent modules will end up increasing steadily. In particular, check to see if 
meaningless functions on a PlayStation 2 such as open(), close(), and write() are called. 
• Pay attention to the library subdivision granularity so that the number of functions contained in a 
single library and the size of the object code are appropriate. 
• Provide APIs for explicitly initializing and terminating the library. 
• Add a function for returning the address of the library entry table structure. 
Since the library entry table structure collects together the functions that the library makes publicly available 
to ERX modules, it can be generated from a library-entry definition file (TBL file) like the one shown below. 
 
Libname sample sample_entry 
Version 1.1 
Entry/8 - 
Entry/8 - 
Entry/8 - 
Entry/8 - 
Entry  SampleInit 
Entry  SampleEnd 
Entry  SampleFunc1 
Entry  SampleAbc 
    : 
 
This example defines version 1.1 of the "sample" library. The functions named SampleInit(), SampleEnd(), 
SampleFunc1(), SampleAbc(), ... are exported to generate the library entry table structure that is to be 
registered in liberx with the label "sample_entry." 
When eelibgen is used to generate the .s file from this TBL file and that .s file is assembled, the library entry 
table structure is generated. Be sure to add a function to the library for returning the address of the library 
entry table structure. An example is shown below. 
 
#include <liberx.h> 
 
extern SceErxLibraryHeader sample_entry; 
 
void *SampleGetErxEntries(void) 
{ 
 return (&sample_entry) 
}

Converting Static Libraries to ERX Format 
To convert a statically linked library (.a file) to ERX format, perform the following steps in addition to those 
steps necessary to support ERX (reviewing the specification again and creating the TBL file). 
1. Identify the ILB files which contain functions that are referenced (imported) by the library. 
2. Use erx-gcc -makestub to generate stubs from these ILB files. 
3. Use erx-gcc to perform partial link and fixup operations. 
Most of the processing is completed by erx-gcc. For details, please see the "ERX Programming" 
document. 
Since the entry function can be omitted in ERX, if you are only converting to ERX format, you are finished 
after performing the above steps. However, for a library that requires initialization or termination processing, 
the programmer is still responsible for making sure that this processing is performed appropriately. If the 
ERX mechanism is used more actively, the entry function can be created so initialization and termination 
processing is performed automatically when the module is started and stopped. The source code for the 
libtimer runtime library is publicly available, and shows an example of this. It can be found at the following

 ERX Library    5-3 
Library Overview 
liberx is a library that is used for implementing a relocatable module execution environment on the EE (a 
relocatable module is a program module that can be relocated at an arbitrary address). Using liberx a 
program can be divided into relocatable modules and placed more freely in memory than if overlays were 
used. 
liberx was created by porting the IOP kernel's system memory management functions, module 
management functions, and library management functions to the EE kernel. This was done in order to 
provide a simple environment in which programs that have been converted to modules can be executed. 
Basically, liberx uses the same mechanism as that of the IOP kernel, however, the two are not completely 
identical because some areas have been modified to work with the EE kernel. 
For details about the environment implemented by liberx, please see the "ERX System Overview," "ERX 
Programming," and "ERX FAQ" documents.

Usage Procedure 
Basic Usage Procedure 
 
1. Initialize the ERX library  
liberx is initialized by calling the sceErxInit() function. liberx requires a memory area for loading modules, 
however, it does not allocate this area itself. The user program should allocate this memory area and 
provide it to liberx. 
 
void *pBuf = memalign(256, ERX_MEMSIZE); 
sceErxInit(ERX_THREAD_PRI, pBuf, ERX_MEMSIZE, ERX_MAX_MODULES); 
 
The first argument of sceErxInit() should specify the priority of the DECI2 ELOADP driver and the module 
loader threads that are created internally by liberx. We recommend that this priority be set higher than the 
priority of any other thread, and as high as possible. Since these threads are normally in WAIT states and 
run only when necessary, they will not interfere with the operation of other threads even if they are set to a 
high priority. 
For the second and third arguments, specify the starting address of the memory area to be managed by 
liberx and its size. 
For the fourth argument, specify the maximum number of modules that can be loaded simultaneously. 
 
2. Export statically linked libraries (registration) 
Libraries that are statically linked to the base ELF should be registered in liberx. Functions of the EE kernel 
(libkernl.a) and functions of liberx are automatically registered. However, to export other libraries, 
processing must be performed to call the set of functions named sce???GetErxEntries() which are provided 
by each library. These functions return the respective ERX library entry tables which must be registered in 
liberx. 
 
// Register libcdvd functions in liberx  
sceErxRegisterLibraryEntries(sceCdGetErxEntries()); 
 
// Register libpad functions in liberx  
sceErxRegisterLibraryEntries(scePadGetErxEntries()); 
 
// Register libipu functions in liberx 
sceErxRegisterLibraryEntries(sceIpuGetErxEntries()); 
: 
 
Libraries that are provided by ToolChain such as libgcc.a, libc.a, and libm.a must also be registered in 
liberx. The required API is provided by the tool chain stub library (libgcc_common_export.a, libc_export.a, 
libm_export.a, etc.) 
 
3. Load modules 
To load an ERX module into memory, call the sceErxLoadModuleFile() function. 
 
modid = sceErxLoadModuleFile(“cdrom0:\\LIBMPEG.ERX”, SCE_ERX_SMEM_LOW, 
NULL); 
 
When this function is called, the address where the module is to be loaded can also be specified.

5-6     ERX Library 
4. Start modules 
To start an ERX module, call the sceErxStartModule() function. 
 
sceErxStartModule(modid, 0, NULL, &result); 
 
To start a module, the libraries on which that module depends must already be registered in liberx. For 
example, since libmpeg depends on libipu, libipu's library entry table must be registered before the 
libmpeg.erx module can be started. If libipu.a is statically linked, registration processing should be 
performed as described earlier. If libipu.erx is dynamically linked, it must be loaded and started before 
libmpeg.erx. 
 
5. Exit the ERX library 
To exit liberx, call the sceErxExit() function. 
Except for the Deci2_Load_Manager module, which is automatically loaded by liberx, all modules that have 
been loaded in memory must be unloaded when the ERX library is exited. If there are still modules 
remaining in memory that have not been unloaded when sceErxExit() is called, the function will terminate 
with an error, and the ERX library will not be exited. 
In addition, memory that was allocated using the sceErxAllocSysMemory() function must be freed by calling 
the sceErxFreeSysMemory() function. If any memory remains that has not been freed, the following warning 
message will be displayed: 
liberx: memory block remained 
To exit the ERX library, all loaded ERX modules must first be stopped and unloaded. Note that after an ERX 
module is stopped, the base ELF cannot call functions that were provided by that ERX module. 
 
6. Reinitialize the ERX library 
After calling the sceErxExit() function and exiting the ERX library, the library can be reinitialized by calling the 
sceErxInit() function again. At this time, functions that had been statically linked to the base ELF in liberx 
must be reregistered by using the sceErxRegisterLibraryEntries() function. 
Loading an Encrypted ERX module 
The procedure for loading an encrypted ERX module from the hard disk drive or a Memory Card (PS2) is 
described below. 
1. Initialize libraries 
To load an encrypted ERX module, not only must you initialize liberx by calling the sceErxInit() function, but 
you must initialize the "DNAS-inst" library as well. In addition, to load an ERX module from a Memory Card 
(PS2), you must initialize either libmc or libmc2 in advance. 
Since liberx calls these libraries using dynamic linking, the libraries must first be registered in liberx. 
 
sceErxRegisterLibraryEntries(sceDNAS2InstGetErxEntries()); 
 
2. Load the encrypted ERX module file 
To load an encrypted ERX module from the hard disk drive, the SCE_ERX_ENCRYPT_DNAS flag must be 
added to the mode argument of a function such as sceErxLoadModuleFile(). 
 
modid = sceErxLoadModuleFile(“pfs1:/libmpeg.erx”, SCE_ERX_ENCRYPT_DNAS, 
NULL); 
 
Note that since the "DNAS-inst" library uses pfs0:, when liberx loads a module, pfs1: or after must be used.
